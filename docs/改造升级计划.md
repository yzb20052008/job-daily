## 1. 背景与目标

### 1.1 现状摘要

「小蓝零工」为日结招工/零工招聘平台，已形成三端一体能力：

- **后端**：JeecgBoot 3.5.1 + Spring Boot 2.7（`qkl-module-job` 承载核心业务）
- **管理端**：Vue2 + Ant Design Vue（运营审核与基础 CRUD）
- **移动端**：UniApp + uView（工人 / 老板双角色）

核心主链路（发岗 → 报名 → 打卡 → 结算 → 评价 → 提现）已基本闭环，并配套认证、积分、VIP、CMS、消息触达等能力。

当前主要短板不在「功能缺失」，而在：

1. 数据库脚本 / 后台菜单与现行 `job_*` 代码存在代差  
2. 订单状态流转偏信任前端，缺少严格状态机  
3. 支付/提现资金链路存在硬编码与未完成回调风险  
4. 运营侧多为通用 CRUD，缺少业务工作台与对账能力  
5. 配置密钥明文、依赖过旧、遗留业务常量混杂  

### 1.2 升级目标

| 目标维度 | 目标描述 | 成功标准 |
|----------|----------|----------|
| 稳定可靠 | 用工闭环与资金链路可生产级运行 | 支付/提现无金额偏差；订单不可非法跳态 |
| 可交付 | 脚本、菜单、文档、环境可一键对齐 | 新环境可按文档完整部署 |
| 可运营 | 审核、异常单、提现、对账可高效处理 | 运营关键动作集中在工作台完成 |
| 可扩展 | 匹配、信用、权益规则可配置演进 | 新增工种/城市/权益无需改核心代码 |
| 可治理 | 密钥、审计、监控、依赖可控 | 无仓库明文密钥；关键链路可告警 |

### 1.3 非目标（本期不做）

- 全量重写为微服务 / 换技术栈  
- 区块链相关能力建设  
- 管理端一次性全面 Vue3 重写（可分期）  
- 无明确业务需求的 ChatGPT 能力扩展

## 2. 范围与原则

### 2.1 改造范围

| 端 | 纳入范围 |
|----|----------|
| 后端 `Job-Daily-Admin` | 订单状态机、支付提现、认证、积分 VIP、定时任务、安全配置、DDL |
| 管理端 `Job-Daily-Web` | 菜单对齐、运营工作台、审核/资金相关页面增强 |
| 移动端 `Job-Daily-Mobile` | 状态展示与交互对齐服务端状态机、异常提示、关键支付提现体验 |
| 数据库 / 运维 | `job_*` DDL、菜单权限、Quartz 任务配置、环境变量治理 |

### 2.2 改造原则

1. **先止血，再增强**：资金与状态机优先于新功能  
2. **服务端为准**：业务规则全部后端校验，前端仅展示与触发  
3. **幂等优先**：支付回调、转账、状态变更必须可重试且不重复记账  
4. **最小破坏**：兼容现网数据与进行中订单，提供迁移脚本  
5. **可回滚**：每阶段具备回退方案与开关控制

## 3. 现状业务架构（基线）

### 3.1 业务主线

```text
工人(member)                 老板(company)                  运营后台
   │                            │                              │
登录/实名/简历               登录/企业认证/发岗               岗审/认证审
浏览/报名/打卡               确认接单/结算                    订单监管
收薪/提现/评价               互评/管员工                      提现审核
积分道具/VIP                 积分道具/VIP                     积分/CMS/统计
```

### 3.2 订单状态机（现行）

```text
0 待确认 → 1 待开工 → 2 工作中 → 3 待结算 → 4 待评价 → 5 已完成
                ↘________________ 6 已取消 ________________↗
```

配套能力：岗位超时下架（`PostJob`）、待确认超时取消（`OrderJob`）。

### 3.3 模块清单

| 模块 | 关键能力 | 主要落点 |
|------|----------|----------|
| 账号角色 | 多端登录、角色切换 | `/api/login`、`/api/user` |
| 招工岗位 | 发布、审核、招满、下架 | `job_post` |
| 用工订单 | 报名、确认、打卡、结算、评价 | `job_order*` |
| 简历认证 | 简历、实名、企业认证 | `job_resume*`、`ums_realname_auth`、`job_company` |
| 钱包资金 | 余额、流水、提现、转账 | `ums_account*`、`ums_withdraw*`、`pay/` |
| 积分 VIP | 签到、道具、套餐 | `integral_*`、`ums_vip*` |
| CMS 消息 | 公告、广告、通知、订阅消息 | `cms_*`、通知服务 |
| 运营后台 | CRUD + 统计 | `views/job|ums|integral|cms` |

## 5. 分期实施计划

> 建议按 **Q1 稳态 → Q2 效率 → Q3 规模** 推进；可按实际人力压缩为 3 个里程碑（M1/M2/M3）。

### 5.1 第一期（P0）：稳态加固（建议 3～5 周）

**目标**：资金安全、状态可信、部署可复现。

#### 工作包 W1：资金链路修复

| 任务 | 说明 | 产出 |
|------|------|------|
| W1-1 | 移除转账金额硬编码，按申请金额/订单金额转账 | 修复 PR + 单测/联调记录 |
| W1-2 | 统一微信/支付宝/浩达回调处理：验签、幂等、状态校验 | `PayCallback` 统一入口 |
| W1-3 | 提现状态机：申请冻结 → 审核 → 打款 → 成功/失败解冻 | 状态枚举 + 服务实现 |
| W1-4 | 资金流水与订单、提现单三方对账脚本/任务 | 日终对账任务 |
| W1-5 | 关键操作审计日志（操作人、金额、前后状态、渠道单号） | 审计表或扩展日志 |

#### 工作包 W2：订单状态机服务化

| 任务 | 说明 | 产出 |
|------|------|------|
| W2-1 | 定义合法状态迁移表（角色 × 当前状态 × 动作 → 下一状态） | 设计说明 + 常量 |
| W2-2 | 改造 `updateOrderStatus` 为服务端动作接口（确认/取消/上班/下班等） | API 改造 |
| W2-3 | 接单人数并发控制（事务 + 锁 / `select for update`） | 防超招 |
| W2-4 | 打卡校验（时间窗、可选地理围栏、图片证据） | 规则可配置 |
| W2-5 | 移动端按新动作接口改造，禁止直传目标状态 | 移动端适配 |

#### 工作包 W3：数据与配置对齐

| 任务 | 说明 | 产出 |
|------|------|------|
| W3-1 | 导出运行库，补齐 `job_*` / `integral_*` / `ums_*` DDL | `db/` 新脚本 |
| W3-2 | 重建后台菜单到 `views/job|ums|integral|cms` | 菜单 SQL |
| W3-3 | 对齐 Quartz：`OrderJob` / `PostJob` / 积分效果任务 | 任务配置 SQL |
| W3-4 | 密钥与敏感配置外置（环境变量 / 配置中心） | 配置规范 |
| W3-5 | 清理仓库内明文密钥，补充 `.gitignore` / 示例配置 | `application-*.yml.example` |

**第一期验收标准**

- [ ] 提现金额与申请金额一致，无测试硬编码  
- [ ] 支付回调重复通知不产生重复入账  
- [ ] 非法状态跳转全部被拒绝并有明确错误码  
- [ ] 新环境可按 DDL + 菜单脚本完成部署  
- [ ] 仓库中无可复现的生产密钥明文

## 6. 关键设计要点

### 6.1 订单动作接口（建议形态）

将「改状态」改为「做动作」，例如：

| 动作 | 允许角色 | 前置状态 | 目标状态 |
|------|----------|----------|----------|
| 老板确认 | company | 0 | 1 |
| 老板拒绝/取消 | company | 0 | 6 |
| 工人上班打卡 | member | 1 | 2 |
| 工人下班打卡 | member | 2 | 3 |
| 结算成功（回调） | system | 3 | 4 |
| 双方评价完成 | member/company | 4 | 5 |
| 超时自动取消 | system | 0 | 6 |

要求：

- 校验操作人是否为订单当事人  
- 校验迁移合法性  
- 写 `job_order_log`  
- 触发通知（失败可异步重试，不影响主事务）  

### 6.2 提现状态机（建议）

```text
待审核 → 审核通过待打款 → 打款中 → 打款成功
   │            │            │
   └─审核拒绝    └─打款失败 ←─┘（可重试 / 终态失败并解冻）
```

### 6.3 数据脚本治理

建议目录结构：

```text
Job-Daily-Admin/db/
  ├── baseline/           # 现行全量 DDL（含 job_*）
  ├── menu/               # 后台菜单与权限
  ├── quartz/             # 定时任务
  └── upgrade/            # 增量升级脚本（按版本号）
```

原则：仓库脚本必须能还原「当前代码可运行」的最小库，而不是历史旧模型。

### 6.4 配置与安全

- 生产密钥仅存环境变量或密钥管理系统  
- 仓库仅保留 `application-*.yml.example`  
- Druid / Actuator 生产关闭或强鉴权  
- 支付回调 IP / 签名强制校验

## 9. 测试与验收

### 9.1 必测场景（M1）

1. 正常完单：报名 → 确认 → 上下班打卡 → 结算 → 评价  
2. 待确认超时自动取消  
3. 招满后不可再确认；并发确认不超招  
4. 非法跳状态（如 0→3、2→5）全部失败  
5. 支付回调重复 3 次仅入账 1 次  
6. 提现：审过打款成功 / 打款失败解冻 / 审核拒绝解冻  
7. 金额边界：0.01、大额、小数精度  

### 9.2 验收产物

- 改造说明（含接口变更清单）  
- 数据库升级脚本与回滚脚本  
- 测试报告（含资金对账样例）  
- 运维配置清单

## 10. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 现网进行中订单与新状态机不兼容 | 卡单 | 上线前存量单清理或兼容映射；灰度开关 |
| 支付渠道差异（微信/支付宝/浩达） | 回调遗漏 | 统一回调适配层 + 渠道开关 |
| 脚本对齐耗时超预期 | 延期 | 优先导出运行库，不强行手工对齐历史 SQL |
| 运营习惯依赖旧菜单 | 使用阻力 | 菜单双轨过渡 1～2 周 |
| 密钥轮换影响短信/OSS/支付 | 短暂不可用 | 分渠道灰度轮换，保留回退配置 |

---

## 11. 回滚策略

1. **应用回滚**：保留上一稳定包；状态机/支付改造用功能开关  
2. **数据回滚**：升级脚本配套 `downgrade`；资金相关禁止静默改历史流水  
3. **渠道回滚**：提现打款可切「仅审核不自动打款」人工模式  
4. **灰度**：先内部账号 → 小流量城市/工种 → 全量
